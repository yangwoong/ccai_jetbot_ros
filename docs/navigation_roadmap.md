# 핵심 임무 로드맵: 지역 인지 순찰

이 프로젝트의 핵심 목표를 기록합니다. YOLO와 LLM(Qwen3-VL-70B)은 이 파이프라인의 핵심 구성요소이며, 아래 우선순위 원칙에 따라 개발합니다.

## 핵심 파이프라인 (목표)

```
1. 이동 가능 바닥면적/장애물 검출 및 회피 (YOLO + 카메라)
   ↓
2. 이동 가능 지역 탐색 및 라벨링 (LLM으로 현관/복도/엘리베이터실/주방/거실 등 주변 상황 인지)
   ↓
3. 내비게이션 지도 생성
   ↓
4. 관리자로부터 순찰 지역 임무 할당
   ↓
5. 순찰하며 이상 상황 감지 및 이벤트 메시지 전송
```

## 우선순위 원칙

1. **임무 수행 안정성이 최우선입니다.** 이동 범위 탐색·장애물 회피가 끊김 없이 동작하는 것이 최신 YOLO 버전을 쓰는 것보다 중요합니다. OpenCV DNN(`cv2.dnn`)으로 YOLOv8 ONNX를 이 Jetson Nano(OpenCV 4.5.0)에서 돌렸을 때 CUDA/CPU 백엔드 둘 다 실측으로 실패한 적이 있어서, **OpenCV DNN 임포터를 우회하고 NVIDIA 자체 TensorRT 런타임(`trtexec`로 빌드한 `.engine` + `ccai_jetbot_patrol/tensorrt_yolo.py`)으로 전면 전환**했습니다. TensorRT가 이 플랫폼에 맞는 정식 추론 경로이기 때문입니다. 그래도 항상 "TensorRT 엔진 → OpenCV DNN ONNX(CUDA→CPU) → HOG/엣지 밀도"의 3단계 자동 폴백을 유지합니다 — 특정 조합이 불안정하면 주저 없이 더 낮은 단계로 내려가되(필요하면 YOLOv8n → YOLOv5n처럼 모델 자체를 낮추는 것도 포함), 로봇이 어떤 상황에서도 최소한 엣지 밀도 회피 + HOG까지는 계속 동작해야 합니다. 자세한 내용은 [docs/vision_and_alerts.md](vision_and_alerts.md)를 참고하세요.
2. **LLM(Qwen3-VL-70B)을 최대한 활용합니다.** 현재는 명령 라우팅(`llm_control_node`)과 위험 요약(`vlm_client_node`) 두 곳에만 쓰이고 있습니다. 아래 2단계(지역 라벨링), 4단계(임무 할당 시 지역명 해석), 5단계(이상 상황 설명)에도 VLM 호출을 적극적으로 추가해야 합니다. 모델은 `.env`의 `CCAI_VLLM_MODEL`로 지정하며 기본값을 `Qwen/Qwen3-VL-70B-Instruct`로 맞춰뒀습니다.

## 단계별 현재 구현 상태

| 단계 | 상태 | 담당 코드 |
|---|---|---|
| 1. 바닥면적/장애물 검출·회피 | **부분 구현 (안정화됨)** | `vision_nav_node`: 엣지 밀도 기반 주행 가능 영역 추정 + YOLO 바운딩박스 + 바닥색 대비 + 프레임 급변을 결합. 방향 플래핑(커밋 `2139244`)과 회피 중 제자리 무한 회전([vision_and_alerts.md §9](vision_and_alerts.md)) 두 가지 실제 충돌 원인을 모두 수정했습니다(스터터 턴 + 최대 회피 시간 상한). 다만 픽셀 단위 "주행 가능 면적" 세그멘테이션은 아직 없고, 엣지 밀도/객체 박스로 간접 추정하는 수준입니다. 키보드 수동 조작([vision_and_alerts.md §10](vision_and_alerts.md))으로 관리자가 언제든 자율 회피를 즉시 오버라이드할 수 있습니다. |
| 2. 지역 탐색 및 라벨링 (LLM) | **부분 구현 (teach-and-repeat + 시각 특징 확인)** | 자동 탐색·자동 라벨링(로봇이 스스로 돌아다니며 이름 붙이기)은 아직 없습니다. 관리자가 수동으로 가르치는 v1: `기억 시작` → 이동 명령들 → `X로 저장해`로 그 경로를 이름 X에 저장(`locations.py`, `data/locations.json`). v1.1로 ORB 시각 특징 캡처/매칭을 추가해서, 이동 시퀀스 드리프트로 엉뚱한 곳에 도착했는지 도착 시점에 시각적으로 확인할 수 있게 됐습니다([vision_and_alerts.md §11](vision_and_alerts.md)). VLM에 의한 자동 분류(현관/복도/주방 등 스스로 인식)는 여전히 미구현이며 다음 단계입니다. |
| 3. 내비게이션 지도 생성 | **부분 구현 (teach-and-repeat)** | 오도메트리·IMU·SLAM이 없어 미터 단위 지도는 만들 수 없습니다. 위 2단계에서 저장한 이동 시퀀스 자체가 "위상 지도"의 최소 형태입니다(이름 → 그 위치까지 가는 timed move 시퀀스). 자동 탐색으로 여러 지점을 잇는 그래프 구조는 아직 없습니다. |
| 4. 관리자로부터 지역 임무 할당 | **구현됨 (v1)** | "정문앞에 택배가 있는지 보고와" 같은 자연어 → LLM이 `{"type":"inspect","target":"정문","text":"택배가 있는지 확인해줘"}`로 해석 → `patrol_node`가 "정문"이 저장된 위치면 그 경로를 재생해서 이동 후 질문에 대해 VLM에게 물어보고 결과를 이벤트로 보고합니다. 위치를 모르면 그 자리에서 확인하고 "위치를 모른다"고 알립니다. |
| 5. 순찰 중 이상 감지 및 알림 | **구현됨** | `vlm_client_node`(RISK/NORMAL 판단) → `patrol_node`(`/ccai/events` 발행) → `telegram_bridge_node`/`web_chat_node`(관리자에게 전달). [docs/vision_and_alerts.md](vision_and_alerts.md) 참고. |

## 구현된 것: 수동 teach-and-repeat 위치 (v1)

오도메트리 없이 진짜 미터 단위 SLAM 지도를 만드는 건 이 하드웨어(휠 인코더/IMU 없음)로는 현실적이지 않습니다. 그래서 "정확한 좌표"가 아니라 "이 이름으로 가려면 이렇게 움직이면 된다"는 **녹화된 이동 시퀀스**를 위치로 취급하는 v1을 구현했습니다.

- **가르치기**: 관리자가 `기억 시작` → `앞으로 가`/`좌회전해` 등으로 로봇을 실제로 이동시킴 → `정문으로 저장해`. 그동안의 timed move 목록이 `data/locations.json`에 이름별로 저장됩니다 (`ccai_jetbot_patrol/locations.py`).
- **임무 수행**: "정문앞에 택배가 있는지 보고와" → LLM이 `inspect`(target="정문", text="택배가 있는지 확인해줘")로 해석 → `patrol_node`가 "정문"이 저장돼 있으면 그 시퀀스를 재생해서 이동 → 도착 후 `vlm_client_node`에 그 질문을 그대로 물어봐서 답을 받아 `/ccai/events`로 보고(`analysis result: 정문: ...`). 텔레그램/웹채팅에 그대로 뜹니다.
- **모르는 위치**: 저장 안 된 이름이면 그 자리에서 확인하고 "위치를 모른다"고 알려줘서, 관리자가 가르쳐야 한다는 걸 바로 알 수 있습니다.
- 관련 코드: `ccai_jetbot_patrol/locations.py`, `patrol_node.py`의 `start_inspect`/`start_replay`/`save_recorded_location`, `vlm_client_node.py`의 질문 기반 분석(`/ccai/vlm_trigger`에 `{"question": "..."}`).
- **v1.1 (시각 특징 확인)**: 저장 시 ORB 키포인트 디스크립터도 함께 캡처하고, 도착 시 현재 프레임과 대조해서 "일치/불일치 가능성"을 이벤트로 보고합니다. 자세한 내용은 [vision_and_alerts.md §11](vision_and_alerts.md)을 참고하세요.

## 자동 탐색·라벨링 (구현됨, v1)

**v1으로 구현 완료** (2026-07-24): 관리자가 매번 수동으로 `기억 시작`부터 가르치지 않아도, "자율탐색" 임무를 주면 로봇이 스스로 돌아다니며 주기적으로 멈춰 관리자에게 위치 이름을 물어보고, 그 답변으로 위치를 저장합니다. 자세한 사용법과 구현은 [docs/vision_and_alerts.md §21](vision_and_alerts.md)을 참고하세요. 원래 계획했던 "VLM이 스스로 현관/복도/주방을 분류"하는 방식이 아니라, **관리자가 라벨을 직접 제공**하는 방식으로 구현했습니다(사용자 요청에 따른 설계 — VLM 자동 분류보다 정확하고, 관리자가 원하는 이름을 붙일 수 있음).

- `patrol_node`에 `PatrolState.EXPLORING` 추가. 주행 자체는 이미 있는 반응형 회피/열린공간추종 로직(D435i 기반, §9·§19)을 그대로 재사용합니다 — 새 주행 알고리즘은 만들지 않았습니다.
- 위치 저장은 이미 있는 `LocationStore`/§11의 시각 특징 캡처 방식을 그대로 재사용합니다(수동으로 가르치나 탐색 중 발견하나 저장 형식은 동일).

## 다음 작업 계획

1. **여러 위치를 잇는 그래프**: 지금은 각 위치가 "시작 지점에서부터의" 독립적인 시퀀스이거나(teach-and-repeat) 시각 특징만 있는 경우(탐색/빠른 저장)입니다. 위치 A에서 위치 B로 가는 경로처럼 위치 간 상대 이동까지 다루려면 그래프 구조로 확장이 필요합니다.
2. **구역 태깅된 이상 알림**: 5단계(이미 구현된 위험 알림)에 현재 위치의 지역 라벨을 붙여서 "복도에서 이상 감지: ..." 처럼 어디서 발생했는지 알 수 있게 합니다.
3. **VLM 기반 자동 분류(선택)**: 관리자가 라벨을 안 줘도 VLM이 "여긴 어디야?" 질문으로 스스로 분류하는 옵션을 자율탐색에 추가할 수 있습니다(`vlm_client_node`의 질문 기반 분석을 그대로 재사용 가능) — 지금은 관리자 라벨링만 구현했습니다.
4. **진짜 SLAM/점유 격자 지도**: D435i 도입 절에서 이미 언급한 `rtabmap_ros` + `nav2` — 여전히 별도의 큰 작업입니다.

## 카메라 하드웨어 고려사항: 모노 RGB vs T265 vs D435i

실제 충돌이 반복되면서 카메라를 Intel RealSense T265/D435i로 바꾸는 것도 검토했습니다. 결론을 기록해둡니다.

- **T265**(스테레오 어안 + IMU, visual-inertial odometry 전용)는 **장애물 회피를 해결하지 못합니다.** 깊이/거리를 재는 센서가 아니라 위치·자세(odometry)를 주는 센서입니다. 대신 이 로드맵의 3단계("내비게이션 지도 생성"이 오도메트리가 없어서 막혀있는 문제)를 T265가 직접 해결해줄 수 있습니다 — 즉 회피용이 아니라 지도/위치추정용 카메라입니다.
- **D435i**(RGB + 실측 깊이 + IMU)는 **장애물 회피 문제 자체에 맞는 센서입니다.** 지금 쓰는 엣지 밀도/바닥색 대비/YOLO 조합은 전부 깊이 센서가 없어서 어쩔 수 없이 쓰는 시각적 우회 추정입니다. 실제 거리를 픽셀 단위로 재는 D435i가 있으면 텍스처/색과 무관하게 훨씬 안정적으로 장애물을 감지할 수 있습니다.
- 현재 방침: 모노 카메라 기반 방식(엣지 밀도 + YOLO + 바닥색 대비 + 프레임 급변, [docs/vision_and_alerts.md](vision_and_alerts.md) 참고)을 먼저 안정화 시도하고, 그래도 충돌이 반복되면 D435i 도입을 권장합니다. T265는 회피 문제와는 별개로, 나중에 3단계(지도 생성)를 진행할 때 다시 고려 대상입니다.

## D435i 도입 (2026-07-23 ~): 실측 깊이 기반 장애물 회피 + CSI 카메라 역할 재정의

모노 카메라 방식을 계속 안정화해봤지만 결국 실측 깊이 센서 도입을 결정했습니다. 동시에 CSI 카메라는 천장을 보도록 마운트를 바꾸고 객체 인식 전용으로만 씁니다(바닥을 볼 수 없으니 장애물 회피용 프록시 신호들은 더 이상 의미가 없음). 아래는 이번에 구현한 것과, 앞으로 남은 것을 구분해서 기록합니다.

### 이번에 구현한 것

- **`scripts/install_realsense_d435i.sh`**: librealsense2를 소스에서 빌드(Jetson은 arm64 apt 패키지가 없고, `-DFORCE_RSUSB_BACKEND=true`로 커널 UVC 드라이버 패치 없이 유저스페이스 백엔드로 빌드 — Jetson 공식 권장 방식)하고, `realsense-ros`(ROS2 래퍼)도 소스로 빌드합니다(`.deb`가 존재하지 않는 arm64 `librealsense2` apt 패키지에 의존하므로 apt 설치는 의존성 해결이 안 됨). udev 규칙도 설치합니다. 컨테이너 안에서 `container_build.sh`와 같은 위치에서 실행합니다. **주의**: 스크립트 안의 태그/브랜치 이름(`REALSENSE_TAG`, `REALSENSE_ROS_BRANCH`)은 이 환경에서 실시간 검증된 값이 아닙니다 — 클론이 실패하면 [librealsense releases](https://github.com/IntelRealSense/librealsense/releases)와 [realsense-ros](https://github.com/IntelRealSense/realsense-ros) 저장소에서 현재 태그/브랜치를 확인하고 환경변수로 지정해서 재실행하세요.
- **`depth_nav_node`** (새 노드, `ccai_jetbot_patrol/depth_nav_node.py`): D435i의 실측 깊이 이미지(`depth_image_topic`, 기본 `/camera/camera/depth/image_rect_raw`)를 받아 전방을 좌/중/우 3분할로 나눠 중앙값 거리를 계산합니다. 중앙 거리가 `obstacle_stop_distance_m`(기본 0.45m)보다 가까우면 장애물로 판정합니다. CSI 버전에서 검증된 상태 머신(방향 커밋-유지, 클리어 확인 프레임, 스터터 턴, 최대 회피 시간 상한 — [docs/vision_and_alerts.md](vision_and_alerts.md) §9)을 그대로 재사용하되, 신호 자체가 실측 거리라서 텍스처/색/조명에 흔들리지 않습니다. 장애물이 없을 때는 좌우 중 더 열린(거리가 먼) 쪽으로 조향하는 "열린 공간 추종" 방식으로 순찰 중 자율 주행을 시도합니다. `patrol_node`가 이미 쓰는 `/ccai/vision_cmd_vel`/`/ccai/vision_status` 토픽에 그대로 발행하므로 `patrol_node`는 수정할 필요가 없습니다 — CSI용 `vision_nav_node`와 이 노드 둘 다 같은 토픽에 발행할 수 있는 구조라, 아래처럼 하나만 활성화합니다.
- **`vision_nav_node.drive_enabled`** 파라미터(기본 `true`): `false`로 두면 CSI 카메라는 YOLO 객체 인식/사람 따라가기/디버그 오버레이는 계속하되, 순찰/수동전진 시 주행 명령(`/ccai/vision_cmd_vel`) 발행은 멈춥니다. D435i가 연결되면 이 값을 `false`로, `depth_nav_node.enabled`를 `true`로 맞춰서 "CSI=객체인식 전용, D435i=주행" 역할 분리를 완성합니다.
- D435i가 실제로 연결된 뒤(2026-07-24)부터는 `config/robot.yaml` 기본값을 `depth_nav_node.enabled: true`, `vision_nav_node.drive_enabled: false`로 바꿔서 D435i가 순찰/수동전진 주행을 담당합니다. CSI+YOLO는 여전히 객체 인식/사람 따라가기/디버그 오버레이 용도로 계속 동작합니다("기존 기능은 문제없도록 유지" 요건 — 주행 담당만 D435i로 넘어가고 나머지는 그대로). D435i 없이 다시 CSI만으로 순찰하려면 그 두 값을 원래대로(`false`/`true`) 되돌리세요.
- `launch/patrol.launch.py`가 `CCAI_ENABLE_DEPTH_NAV=1`일 때 `depth_nav_node`뿐 아니라 `realsense2_camera` 드라이버 자체도 같이 실행합니다(`rs_launch.py`를 `enable_depth:=true enable_color:=false`로 include) — 별도로 `ros2 launch realsense2_camera ...`를 수동 실행할 필요가 없습니다. 다른 방식으로 이미 realsense 드라이버를 띄워둔 상태라면 `CCAI_ENABLE_REALSENSE_DRIVER=0`으로 이 부분만 끌 수 있습니다.
- `scripts/host_docker_run.sh`는 이제 `CCAI_ENABLE_DEPTH_NAV`(안전모드 여부에 따라 기본 0/1)를 컨테이너에 전달하고, D435i가 쓰는 raw USB 버스 접근(`-v /dev/bus/usb:/dev/bus/usb`, `--device-cgroup-rule "c 189:* rmw"`)을 자동으로 추가합니다. **기존에 떠 있는 컨테이너를 `docker restart`만 하면 이 새 환경변수/디바이스 마운트가 적용되지 않습니다** — `docker run` 시점에 고정되므로, 반드시 `scripts/host_docker_run.sh`를 다시 실행해서 컨테이너를 재생성해야 합니다.

### 호스트 Wi-Fi(iwlwifi)가 반복 크래시하는 문제 (2026-07-25, 해결됨)

호스트의 Intel AC 8265 Wi-Fi 카드가 `dmesg`에 아래 패턴을 반복하며, SSH/웹 접속이 계속 느려지거나 끊기는 문제가 실기에서 발생했습니다.

```
iwlwifi 0000:01:00.0: Queue 2 stuck for 10000 ms.
iwlwifi 0000:01:00.0: Microcode SW error detected. Restarting 0x2000000.
```

**디버깅 과정에서 배제된 원인들** (전부 실기로 확인):
- PCIe ASPM 절전 상태 — 런타임 정책(`performance`)과 커널 부트 인자(`pcie_aspm=off`) 둘 다 걸어봤지만 크래시가 똑같이 반복됨. 완전히 배제.
- CPU 기아(starvation) — 크래시 구간의 `tegrastats`가 CPU 25~35%대로 전혀 포화 상태가 아니었음. 배제.
- 약한 신호/채널 품질 — `iw dev wlan0 link`에서 `signal: -28~-29 dBm`(매우 좋음), `tx bitrate: 300 MBit/s`, `tx retries: 1`, `tx failed: 0`. 배제.
- D435i/`visual_odom_node`의 USB 부하 — `CCAI_ENABLE_VISUAL_ODOM=0`(align_depth 끔, visual_odom_node 자체를 안 띄움)으로도 재현 시도했으나 무관하다는 게 최종적으로는 아래 확정 원인으로 대체됨.

**확정 원인**: 유선 랜을 연결한 채 무선 IP로 SSH 접속해 두고 유선 케이블을 뽑는 재현 테스트로 확정했습니다. 유선이 끊기는 순간 그동안 `eth0`(낮은 metric, 우선 경로)를 타던 모든 연결(`telegram_bridge_node`의 폴링/전송, `vlm_client_node`의 클라우드 호출 등)이 한꺼번에 `wlan0`로 재시도되면서, **여러 연결이 동시에 몰리는 버스트 트래픽**이 발생합니다. 이게 이 카드/드라이버/펌웨어(로드된 펌웨어 버전 `22.391740.0`) 조합의 802.11n 프레임 집계(aggregation) 큐 처리 버그를 건드려 워치독이 걸리는 것으로 확인됐습니다. 컨테이너 최초 기동 직후(194초 시점)에 크래시가 시작됐던 것도 같은 메커니즘 — 여러 노드가 동시에 외부로 연결을 시도하며 트래픽이 몰린 것.

**적용한 수정**: `scripts/host_fix_iwlwifi_stability.sh`(신규) — `/etc/modprobe.d/iwlwifi.conf`에 `options iwlwifi 11n_disable=1 power_save=0 uapsd_disable=1`을 써서 11n 프레임 집계를 끕니다. **재부팅이 있어야 적용됩니다** (모듈 옵션이라 iwlwifi가 다시 로드될 때만 반영). `host_docker_run.sh`가 매번(D435i 활성화 여부와 무관하게, 이 문제 자체가 D435i와 무관했으므로) 이 스크립트를 실행해서 설정 파일이 없거나 다르면 새로 씁니다.

**검증**: 재부팅 후 무선 IP로 SSH 접속한 채 유선 케이블을 뽑는 재현 테스트를 다시 했고, 이번엔 크래시/연결 끊김이 전혀 발생하지 않았습니다. 확정.

이제 쓸모없어진 `host_fix_iwlwifi_aspm.sh`(ASPM 완화책)는 삭제했습니다.

### 새로 발견된 문제: `soctherm: OC ALARM` + D435i가 USB에서 다시 사라짐 (2026-07-25, 미해결)

Wi-Fi 문제를 재부팅으로 재현 테스트하던 중 콘솔에 `soctherm: OC ALARM 0x00000001`이 연속으로 찍히기 시작했고, 그 시점에 `lsusb -t`를 보면 D435i가 USB 트리에서 다시 사라져 있었습니다(`Bus 02` 5000M 허브 아래에 Video 인터페이스들이 없음).

**추정 (미검증)**: `OC ALARM`은 Jetson Nano의 SoC 전류 모니터링(soctherm)이 과전류를 감지했다는 경보입니다. Jetson Nano는 기본 마이크로 USB 전원(5V/2A, 10W)으로는 D435i(USB3 고대역폭 스트리밍) + CSI 카메라 + Wi-Fi + 모터를 동시에 감당하기 빠듯한 것으로 잘 알려져 있어서, 과전류가 감지되면 보호 차원에서 포트 전원이 끊기며 D435i가 USB에서 탈락했을 가능성이 있습니다.

**다음에 확인할 것**:
1. 현재 이 로봇이 마이크로 USB(5V/2A)로 전원을 받는지, 아니면 DC 배럴잭(5V/4A) + J48 점퍼 방식인지 확인.
2. 마이크로 USB라면 배럴잭 전원(5V/4A 이상 정격 어댑터) + J48 점퍼로 전환 — Jetson Nano에서 이 증상의 표준적인 해결책.
3. 전환 후에도 `OC ALARM`이 재발하는지, D435i가 USB에서 안정적으로 유지되는지 재확인.

## SLAM/Nav2 포기 → 경량 커스텀 좌표 컨트롤러로 전환 (2026-07-24)

`rtabmap_ros`/`nav2`(`navigation2`, `nav2_bringup`)/`robot_localization` 4개 패키지 모두 이 이미지의 apt 저장소에 **없는 것으로 확정**됐습니다(`scripts/install_slam_nav2.sh` 실행 결과, 전부 `E: Unable to locate package`). 이 이미지는 ROS2 Humble을 bionic에 백포트한 커스텀 조합이라 흔한 패키지도 종종 빠져 있는데(`xacro`/`diagnostic_updater` 전례), 이번엔 그 빠진 패키지가 각각 수십 개 하위 패키지짜리 큰 스택(`nav2`)이거나 g2o/GTSAM/PCL 같은 무거운 C++ 코어(`rtabmap`)를 필요로 해서, Jetson Nano 4GB RAM으로 소스 빌드를 시도하는 건(이미 pycuda/librealsense2 빌드에서 여러 번 겪은 메모리 문제 감안) 이번 세션의 "한 패키지씩 대응" 전례와는 위험도가 다르다고 판단했습니다.

**사용자가 명시적으로 선택한 방향**: "경량 대안: 직접 만든 좌표 컨트롤러." Nav2/rtabmap 전체를 대체하는 대신, 이 프로젝트 자체에서 다음 세 가지를 새로 구현했습니다.

1. **`visual_odom_node.py`(신규)**: D435i의 컬러+정렬된깊이 프레임으로 직접 만든 RGB-D 시각 오도메트리. ORB 특징점 매칭 → 깊이로 3D 역투영 → Kabsch 알고리즘(SVD 기반 강체변환 추정)으로 프레임 간 카메라 이동을 구해 누적 `(x, y, yaw)` 포즈를 `/ccai/odom_pose`로 발행하고 `odom`→`base_link` TF도 방송합니다. **루프 클로저도, 포즈 그래프 최적화도, 점유 격자 지도도 없는 순수 프레임 간 오도메트리라 시간이 지나면 반드시 드리프트합니다** — 한 세션 안에서 "대략 원래 자리로 돌아가는" 용도지, 튜닝된 진짜 SLAM 스택의 정확도를 대신하지 못합니다.
2. **`patrol_node`의 점-대-점 컨트롤러 (`PatrolState.POSE_GOAL`)**: 목표 좌표까지 방향 오차가 크면 제자리 회전으로 먼저 정렬하고, 아니면 목표에 가까워질수록 속도를 줄이며 전진 + 소폭 방향 보정하는 단순 비례 제어(`compute_steering_twist`/`compute_pose_goal_twist`). `depth_nav_node`의 `obstacle_now` 신호를 안전 우선순위로 확인해서, 실제 장애물이 감지되면 그 회피 명령이 이 컨트롤러의 명령을 덮어씁니다.
3. **커버리지 기반 탐색 알고리즘 (`pick_explore_subgoal`/`compute_explore_twist`)**: rtabmap 없이는 진짜 점유 격자가 없으므로, 대신 시각 오도메트리 좌표를 굵은 격자 셀로 나눠 방문 횟수를 기록하고(`self.visited_cells`), 주기적으로 로봇 주변 여러 방향/지점 후보를 샘플링해서 **가장 덜 가본 셀**로 이어지는 후보를 골라 그 지점까지 위 점-대-점 컨트롤러로 이동합니다. 이게 원래 문제("좌우로 피하기만 하고 안 가본 길을 못 찾음")를 직접 겨냥한 부분 — 이제 탐색 중 이미 지나온 곳인지 아닌지를 실제로 구분합니다.

### 활성화 절차

```bash
CCAI_ENABLE_VISUAL_ODOM=1 ./scripts/host_docker_run.sh
```
```yaml
# config/robot.yaml
patrol_node:
  ros__parameters:
    explore_frontier_mode: true   # true면 EXPLORING이 커버리지 탐색 알고리즘으로 주행, false면 기존 반응형 그대로
visual_odom_node:
  ros__parameters:
    enabled: true
```

둘 다 기본값이 꺼져 있어서, 아무것도 건드리지 않으면 기존 반응형 `depth_nav_node` 순찰이 그대로 동작합니다(안전망 유지).

"정문으로 가"/"정문에 뭐 있는지 확인해줘" 같은 임무는 `patrol_node.start_replay()`가 저장된 위치에 `pose`가 있고 최근 오도메트리 신호(`has_recent_odom()`, 기본 2초 이내)가 있으면 위 점-대-점 컨트롤러(`POSE_GOAL`)로 실제 좌표까지 이동합니다. `pose`가 없거나 오도메트리가 끊겼으면 기존 타임드 재생/시각 전용 위치 확인으로 자동 폴백합니다.

### 버그: `explore_frontier_mode: true`로 켜도 알고리즘이 안 바뀌던 문제 (2026-07-25, 수정됨)

실기 테스트에서 `explore_frontier_mode: true` + `visual_odom_node.enabled: true`로 켰는데도 로봇이 기존과 똑같이 제자리 회전만 반복하고 새 커버리지 탐색으로 전혀 나아가지 못하는 문제가 발생했습니다("알고리즘에 변화가 없어").

**원인**: `depth_nav_node.py`의 주행 조건이 `self.mode in ("patrolling", "exploring", "pose_goal")`이라, `explore_frontier_mode`가 켜져 있어도 `patrol_node`가 `EXPLORING`/`POSE_GOAL` 상태이기만 하면 depth_nav_node는 상관없이 **자기 자신의(예전) 반응형 좌우 조향 알고리즘을 계속 계산해서 `/ccai/vision_cmd_vel`/`/ccai/vision_status`(obstacle_now 포함)에 발행**하고 있었습니다. 그런데 `patrol_node.drive_loop()`의 안전 오버라이드가 "`obstacle_now`가 true면 depth_nav_node가 최근에 발행한 twist를 그대로 채택"하는 방식이었는데, 로봇이 가구/벽으로 둘러싸인 방 안을 탐색하는 동안 `obstacle_now`는 사실상 거의 항상 true라서 — **이 오버라이드가 거의 매 tick 발동해서 새 커버리지 알고리즘의 twist를 depth_nav_node의 옛 반응형 twist로 계속 덮어썼습니다.** 즉 새 알고리즘 코드 자체는 정상 동작했지만, 안전장치가 사실상 항상 옛 알고리즘으로 되돌리고 있었던 것 — "알고리즘 변화 없음"이라는 증상과 정확히 일치합니다.

**수정**:
1. `depth_nav_node.py`에 `explore_frontier_mode` 파라미터(패트롤 노드와 동일한 값으로 `robot.yaml`에서 맞춰줌) 추가 — 이게 true면 `EXPLORING` 상태에서 더 이상 주행하지 않고(=경쟁하는 cmd_vel을 안 보냄) 장애물 센싱(`obstacle_now`)만 계속 최신 상태로 발행합니다. `POSE_GOAL`은 항상 depth_nav_node가 주행하지 않도록 이미 되어 있었습니다(패트롤 노드의 점-대-점 컨트롤러 전용).
2. `patrol_node.py`의 안전 오버라이드를 "depth_nav_node의 twist를 그대로 채택"에서 "`obstacle_now`면 그냥 정지(`stop_motion()`)"로 단순화 — EXPLORING의 경우 정지와 함께 `self.explore_sub_goal = None`으로 목표도 버려서, 다음 tick에 막힌 방향이 아닌 새 후보 방향을 다시 샘플링하도록 했습니다.

**검증**: 코드 리뷰로 원인을 특정하고 수정했습니다 — 위 두 파일 모두 컴파일 확인은 했지만, 이 특정 수정이 실기에서 실제로 "제자리 회전" 없이 전진하는지는 아직 재검증이 필요합니다.

### 아직 검증 안 된 것 (정직하게)

- **카메라↔로봇 축 매핑 미검증**: 카메라 광학 좌표계(x=오른쪽, y=아래, z=전방)와 로봇 평면 좌표계(x=전방, y=왼쪽, yaw=위에서 봤을 때 반시계)의 대응이 실기에서 검증되지 않았습니다. 방향이 반대로 나오면 `visual_odom_node`의 `yaw_sign`/`lateral_sign`/`forward_sign` 파라미터(기본 전부 `1.0`)를 `-1.0`으로 뒤집어서 조정해야 합니다.
- **드리프트 정도 미측정**: ORB 매칭+Kabsch 정확도가 이 조명/텍스처 환경에서 실제로 얼마나 드리프트하는지 실기 데이터가 없습니다. `pose_goal_tolerance_m`(기본 0.15m)이 그 드리프트 대비 너무 빡빡하거나 헐거울 수 있습니다.
- **커버리지 격자 파라미터 미튜닝**: `explore_visited_cell_size_m`(0.5m), `explore_step_distance_m`(0.8m), `explore_candidate_count`(8)는 첫 합리적 추정값이지 실기로 조정된 값이 아닙니다.
- **`align_depth.enable` 대역폭/성능 영향 미확인**: D435i가 컬러+깊이+정렬 파이프라인을 동시에 돌릴 때의 USB 대역폭 여유는 실측하지 않았습니다(과거 "USB CAM overflow" 전례 있음 - 위 §D435i 도입 참고).

## 방-단위 탐색: 45도 회전 + 특징 인식 + 천장 형태 기반 이동 (v3, 2026-07-27, 실기 미검증)

커버리지 탐색(위 §)의 점-대-점 컨트롤러가 `visual_odom_node`의 yaw 추적에 의존하는데, 실기에서 회전 중 yaw가 실제 회전량을 제대로 못 따라간다는 게 확인되면서 그 컨트롤러 자체가 회전에서 못 벗어나는 문제가 있었습니다. 그래서 **오도메트리에 전혀 의존하지 않는 시간 기반 방식**으로 탐색 알고리즘을 새로 만들었고(v1, 2026-07-26), 실기 테스트에서 나온 문제(회전 오버슈트, 장애물 미회피, 한 지점만 탐색하고 멈춤)를 거쳐 v2(07-27 오전) → v3(07-27, 이 절)로 다듬었습니다. 이 절이 **현재 최신 알고리즘**입니다.

### 파이프라인

```
1. 제자리에서 45도씩(설정 가능, 시간 기반 - 아래 "왜 시간 기반" 참고) 회전 - 총 8단계로 360도
   ↓ (각 단계마다: 정지 → 잠깐 대기(settling, 블러 방지) → 그제서야 촬영)
   D435i 정면 영상을 VLM에 보내 "이 방향에 뭐가 보이는지 + 이동 가능한지" 질문
   → 방향(단계)마다 특징 설명을 전부 기억 (이동 가능/불가 여부도 같이 기록)
   ↓ (한 바퀴 다 돌면, 마찬가지로 정지 → 대기 → 촬영)
2. CSI(천장) 영상을 VLM에 보내 "천장 모양/공간 크기 + 계속 탐색하기 좋은 방향(왼쪽/오른쪽/직진/후진)" 질문
   → 천장 설명과 방향 힌트를 기억
   ↓
3. 관리자에게 이 지점의 이름을 물어봄 → LocationStore에도 동일 라벨로 등록(기존 "X로 가"/순찰 명령과 호환)
   ↓
4. 1에서 "이동 가능"으로 기록된 방향들 중, 2에서 받은 천장 방향 힌트와 가장 가까운 방향을 선택
   → 그 방향으로 시간 기반 회전+직진 이동 → 새 지점 도착 → 1번부터 반복
   (= "천장 모양을 보고 이동 방향을 고르고, 도착하면 다시 45도 회전하며 주변 특징을 확인"하는
   흐름이 매 지점마다 반복되는 구조 - 2번의 질문 결과가 다음 이동 방향을, 1번의 결과가
   그 지점에서 실제로 갈 수 있는 후보를 결정)
   ↓ (이동 가능한 방향이 더 없으면)
5. 시간 기반 회전+직진으로 이전 지점까지 후진(역추적) → 그 지점의 다음 미탐색 방향 시도
   ↓ (루트 지점까지 후진했는데 더 갈 곳이 없으면)
6. 탐색 완료
```

이게 사용자가 요청한 3단계와 대응되는 부분:
1. "45도 회전하며 영상을 LLM에 전송하여 특징을 요청하고 기억" → 파이프라인 1번.
2. "천장의 형태를 보고 이동할 수 있는 방향으로 이동하며, 확인 못한 특징이 보이면 제자리 45도 회전하며 탐색" → 파이프라인 2·4번(천장 힌트로 방향 선택)이 이동을, 매 새 지점 도착 시 자동으로 다시 시작되는 1번(전체 45도×8 스윕)이 "새로운 곳에 도착하면 주변을 다시 확인"하는 부분을 담당합니다. (실시간으로 "이동 중에 새로운 게 보이면 즉시 정지"하는 것까지는 구현하지 않았습니다 - 그러려면 이동 중 계속 VLM을 호출해야 하는데 비용/지연이 커서, 대신 "새 지점에 도착할 때마다 매번 새로 스윕한다"는 형태로 단순화했습니다. 아래 "아직 검증 안 된 것" 참고.)
3. "이동시 천장 모양 따라 방향 선택, 모르는 곳으로 계속 이동하며 지도로 활용" → 파이프라인 4번(천장 힌트 기반 방향 선택) + `RoomGraph`가 지점 간 연결과 각 지점의 관찰 특징 전체를 누적 저장하는 것이 "지도" 역할을 합니다.

### 왜 시간 기반(오도메트리 미사용)인지

`visual_odom_node`의 yaw가 회전 중 실제 회전량을 못 따라가는 게 확인되어서, 이 알고리즘은 **yaw를 아예 참조하지 않고** 시간만큼만 회전/직진합니다. 첫 구현(v1, 07-26)은 `angular_speed` 파라미터가 실제 물리적 rad/s와 같다고 가정한 공식(`(2π/N) / angular_speed`)을 썼는데, 실기에서 45도를 목표로 2바퀴 반을 도는 걸로 확인됐습니다 — 바퀴에 인코더가 없어서 "명령값 = 실제 각속도"라는 가정 자체가 성립하지 않았던 것입니다. v2(07-27)부터 공식을 버리고 **회전 전용의 낮은 속도**(`explore_room_scan_angular_speed`, 기본 0.09)와 **직접 튜닝하는 초 단위 시간**(`explore_room_scan_turn_seconds`, 기본 1.0초)으로 바꿨습니다 — 실기에서 스톱워치/각도기로 직접 재서 이 값을 맞추는 것 외에는 인코더 없이 검증할 방법이 없습니다. 여러 지점을 거칠수록 방향 오차가 누적되는 건 여전한 정직한 한계입니다.

### 구현

- **`ccai_jetbot_patrol/explore_graph.py`**: `RoomGraph` 클래스 - 각 지점을 노드로, 스윕 중 관찰한 **모든 방향의 특징**(`observations`: 방향별 설명 + 이동 가능 여부 + 시도 여부)과 천장 설명, 부모 지점(어느 방향으로 들어왔는지)을 저장. **진짜 도면이 아니라 위상 그래프 + 방향별 특징 목록**입니다(치수/좌표 없음, "이 지점에서 이 방향은 이렇게 생겼다"만 기록) - 점유 격자 SLAM이 없는 이 로봇 센서 구성으로는 실측 도면 자체가 불가능해서 사용자와 상의해 이 방식으로 결정했습니다. `data/room_graph.json`에 저장.
- **`ccai_jetbot_patrol/patrol_node.py`**: `explore_room_scan_mode: true`(기본값)일 때 `EXPLORING` 상태를 `tick_room_scan()`이 전담합니다. 회전(`rotating`) → 대기(`settling`, 블러 방지) → VLM 질문(`await_vlm_step`, D435i) → (한 바퀴 다 돌면) 대기 → 천장 질문(`await_ceiling`, CSI) → 라벨 확인(`await_label`) → 이동(`advance_doorway`) 또는 후진(`backtrack_advance`)의 상태기계. `depth_nav_node`의 `obstacle_now`를 매 틱 확인해서 장애물이 있으면 회전/직진 모두 즉시 멈춥니다.
- **천장 방향 힌트로 이동 방향 선택** (`room_scan_pick_doorway`): 천장 질문 응답에서 "왼쪽/오른쪽/직진/후진" 중 하나를 파싱해서(`parse_ceiling_direction_hint`), 그 방향에 각도상 가장 가까운 **미시도 이동가능 방향**을 고릅니다. 힌트가 없거나 파싱 실패하면 스윕에서 발견한 순서대로 첫 번째 것을 씁니다.
- **모든 방향의 특징을 기억, 이동가능 여부는 별도 태그**: 원래(v1)는 "출입구가 보이는가"만 물었는데, "이 방향에 보이는 것 + 이동 가능한지"로 질문을 넓혔고(`GO:YES`/`GO:NO`), 이동 불가 방향의 설명도 버리지 않고 `RoomGraph`에 같이 저장합니다(사용자가 "특징을 기억"하라고 명시적으로 요청한 부분).
- **회전/이동 후 반드시 대기(settling) 후에만 VLM 호출**: 정지 → `explore_room_scan_settle_seconds`(기본 1.0초) 대기 → 그제서야 VLM 질문. 회전 스텝 사이, 천장 질문 전, 그리고 **새 지점에 막 도착했을 때**(v2에서 빠뜨렸던 부분, v3에서 추가) 모두 동일하게 적용됩니다 - 회전이든 직진이든 멈춘 직후엔 카메라 파이프라인에 블러 프레임이 남아있을 수 있어서, 어느 쪽이든 촬영 전에는 반드시 거칩니다.
- **후진(역추적) 각도 계산**: 새 지점에 도착하면 그 지점의 "0단계" 방향은 항상 "더 안쪽"이고 들어온 방향은 항상 정반대(180도, `explore_room_scan_headings/2`단계)에 있다는 기하학적 사실을 이용합니다. 후진해서 이전 지점에 재진입하면, 원래 나갈 때 썼던 방향 번호(`k`)로 `-(k + N/2) mod N`만큼 추가 회전해서 이전 지점의 원래 0단계 기준을 복원합니다.
- **`depth_nav_node`의 장애물 미회피 버그 수정**: `region_distance()`가 "유효한 깊이 값이 하나도 없으면 무조건 완전히 열려 있다고 판단"하던 버그를 고쳤습니다(너무 가까워서 깊이를 못 재는 상황과 진짜 빈 공간을 구분). `obstacle_stop_distance_m`도 0.45m → 0.6m로 올렸습니다.

### 버그: 회전 단계가 정면 장애물 신호에 막혀 영원히 멈추는 문제 (2026-07-27, 수정됨)

실기 테스트에서 "0도 방향 특징: NO 벽과 가구로 막힘"을 로그에 남긴 뒤 다음 45도로 전혀 못 넘어가고, `depth_nav_node`의 "D435i depth frames stopped arriving" 경고만 반복되며 멈추는 문제가 발생했습니다.

**원인**: `tick_room_scan()`의 `rotating` 단계가 (전진 단계와 똑같이) `is_obstacle_now()`를 매 틱 확인하도록 되어 있었는데, **제자리 회전은 앞으로 나아가지 않으므로 정면 장애물 여부와 원래 무관**해야 합니다. 게다가 이 순간 D435i 깊이 스트림이 끊기면서(하드웨어 문제 - 아래 참고) `depth_nav_node`가 마지막으로 계산했던 `obstacle_now` 값을 그대로 얼려서(freeze) 계속 재발행했고, 하필 그 값이 `true`였던 탓에 회전 단계가 "장애물 있음"으로 영원히 착각해 `stop_motion()`만 반복했습니다.

**수정**: (1) `rotating` 단계에서 장애물 체크를 아예 제거했습니다(전진하는 `advance_doorway`/`backtrack_advance`만 계속 체크). (2) `is_obstacle_now()`가 `depth_nav_node`의 상태가 `depth_camera_timeout`(깊이 프레임이 끊겼다는 뜻)이면 얼어붙은 값을 믿지 않고 "장애물 미확인"(false)으로 처리하도록 고쳤습니다 - 카메라가 죽은 것과 실제 장애물이 있는 것은 다른 상황이라는 걸 명시적으로 구분.

**여전히 미해결**: D435i 깊이 프레임이 실제로 왜 끊겼는지(이전에 확인된 `soctherm OC ALARM`/전원 공급 부족 의심과 같은 문제일 가능성)는 이번 수정과 별개로 원인 규명이 필요합니다 - 위 "새로 발견된 문제: soctherm OC ALARM" 절 참고.

### 실기 확인 3건 추가 수정 (2026-07-27)

- **웹챗 프리뷰 3개가 줄바꿈됨**: `.cameras img`에 고정 픽셀 폭(320px→296px)을 줬던 게 실제 렌더링 폭과 안 맞아 여전히 줄바꿈됐습니다. 고정 폭 대신 `flex: 1 1 0` + `flex-wrap: nowrap`으로 바꿔서, 실제 컨테이너 폭이 얼마든 상관없이 항상 3등분되도록 했습니다.
- **D435i 오버레이가 깔끔한 초록 blob이 아니라 산발적인 빨강/노랑 얼룩으로 나옴**: 픽셀 단위로 바로 칠하던 방식이라 노이즈가 그대로 보였습니다. 이제 열린 바닥(depth > `obstacle_stop_distance_m`) 픽셀에 모폴로지 opening/closing(작은 노이즈 제거 + 작은 구멍 메움)을 적용하고, **가장 큰 연결된 영역 하나만** 윤곽선으로 찾아 채워서 그립니다(전체 프레임의 1% 미만인 작은 얼룩은 무시). 주행 로직에서 실제로 안 쓰이던 "주의(노랑)" 3단계 분류도 없앴습니다(초록/빨강 2단계로 단순화) - 시각적 노이즈만 줄이는 변경이라 주행 로직에는 영향 없습니다.
- **회전이 45도가 아니라 90도가량 되는 걸 확인**: 인코더가 없어서 정확한 45도로 재보정하는 대신, 사용자 지시대로 **현재 회전 속도/시간(`explore_room_scan_angular_speed`/`explore_room_scan_turn_seconds`)은 그대로 두고**, 실측된 회전량(90도)에 맞춰 `explore_room_scan_headings`를 8→4로 바꿔서 한 바퀴(360도)에 4장만 촬영/분석하도록 했습니다. 나중에 속도/시간을 다시 튜닝하면 그때 실제 회전량을 다시 재서 `360 / 실측각도`로 `explore_room_scan_headings`를 다시 계산해야 합니다.

### 실기 확인 2건 추가 수정 (2026-07-27, 2차)

- **D435i 오버레이가 여전히 바닥을 빨강으로 잘못 표시**: 위 blob 처리 수정 후에도, 로봇 바로 앞/아래 바닥이 초록이어야 하는데 빨강으로 나오는 문제가 있었습니다. 원인은 오버레이의 분석 영역이 프레임 하단 끝(로봇 바로 앞)까지 포함하고 있었던 것 - **카메라 시야각상 로봇 바로 앞 바닥은 실제 장애물 유무와 무관하게 항상 가장 가까운(depth 값이 가장 작은) 지점**이라, 단순 절대거리 임계값으로는 항상 "가깝다=위험"으로 오판합니다. 실제 주행 판단 로직(`analyze_depth`)이 애초에 이 구간(하단 25%)을 빼고 0.35~0.75 구간만 쓰고 있었는데, 시각화(`build_drivable_overlay`)만 하단 끝까지 포함하고 있어서 로직과 화면이 서로 다른 걸 보고 있었습니다 - 오버레이도 같은 0.35~0.75 구간으로 맞췄습니다.
- **탐색이 관리자가 정지시키지 않았는데도 스스로 멈춤**: 루트 지점에서 이동 가능한 방향을 하나도 못 찾으면 곧바로 "탐색 완료"로 멈췄는데, `explore_room_scan_headings`를 8→4로 줄인 뒤라 한 바퀴에 4곳만 확인하다 보니 진짜 갈 곳을 놓치고도 쉽게 "완료"로 잘못 판단할 가능성이 커졌습니다. "별도로 명령하지 않는 한 임무를 끝까지 수행"하라는 요청에 따라, 갈 곳을 못 찾으면 즉시 멈추지 않고 **한 스텝만큼 방향을 바꿔서 다시 스윕**하는 걸 `explore_room_scan_max_root_retries`(기본 3)번까지 재시도한 후에야 진짜로 "탐색 완료"를 선언하도록 바꿨습니다. 재시도 스윕은 이미 확보한 라벨/천장 설명은 다시 안 묻고 방향 확인만 반복합니다.

### LLM이 장애물 판단에 적극 개입 (2026-07-27, 3차)

실기 로그로 정확한 패턴이 확인됐습니다: VLM이 두 방향 모두 "이동 가능"(`GO:YES`)으로 판단했는데, 실제로 그 방향에 전진을 시작하자마자 `depth_nav_node`의 실측 깊이 기반 장애물 임계값(`obstacle_stop_distance_m`, 0.6m)에 걸려서 즉시 포기됐습니다. 두 후보 다 이렇게 소진되고, 이후 재시도 스윕에서도 매번 같은 임계값에 걸려 전부 "NO"만 나오다 결국 "탐색 완료"로 끝났습니다 - **VLM은 "갈 수 있다"고 봤는데 단순 거리 임계값이 그 판단을 무시하고 있던 것**입니다(가구 사이 좁은 틈처럼, 실측 거리로는 가깝지만 실제로는 지나갈 수 있는 경우를 depth 센서 혼자서는 구분 못함).

**수정**: `advance_doorway` 중 장애물이 감지되면, 이전에는 그 방향을 즉시 포기했는데 이제는 **정지 → 근접 사진을 다시 VLM에 보내 "정말 막혔는지, 좁아도 지나갈 틈이 있는지" 재확인**(`PASS:YES`/`PASS:NO`)하는 단계를 거칩니다. VLM이 지나갈 수 있다고 하면 전진을 재개하고(단, `depth_nav_node`의 실시간 안전 정지는 그대로 유지 - 이 재확인은 "포기할지 말지"만 결정할 뿐 물리적 안전장치 자체를 끄지 않습니다), 정말 막혔다고 하면 그때 포기합니다. 무한 재시도를 막기 위해 같은 방향 시도당 `explore_room_scan_max_obstacle_overrides`(기본 2)회까지만 재확인을 허용합니다.

### 방을 나가지 않았는데 나갔다고 오판 + 재시도가 같은 방향만 재확인 (2026-07-27, 4차)

실기 로그에서 두 가지 추가 문제가 확인됐습니다.

1. **짧은 이동(30~40cm)마다 매번 "새 방"으로 취급**: 출입구로 보이는 방향을 통과하면 무조건 `room_scan_enter_new_room()`을 호출해서 새 지점을 만들고 전체 스윕+라벨 요청을 처음부터 다시 했는데, 실제로는 같은 방 안에서 조금 이동한 것뿐이었습니다(사용자가 지적한 대로 천장의 형광등 배치가 끊김없이 이어지는 걸 보면 방을 나간 적이 없음). "사무실 중앙"이라는 같은 라벨을 세 번 연속 물어본 게 이 증상입니다.
   **수정**: 통과 직후 바로 새 방을 만들지 않고, **CSI VLM에게 "방금 전 위치의 천장 특징이 이거였는데, 지금 보이는 천장이 끊김없이 이어지는 같은 공간인지 아니면 정말 새 방으로 들어온 건지" 재확인**(`NEWROOM:YES`/`NEWROOM:NO`)을 거칩니다. 같은 공간이라고 판단되면 새 지점을 만들지 않고 그 자리에서 다른 방향을 계속 찾습니다.
2. **재시도가 원래 스윕과 정확히 같은 4방향만 다시 봄**: `explore_room_scan_headings=4`(90도 간격)에서 재시도할 때 "1스텝(90도)"만큼 방향을 바꿨는데, 90도 격자에서 90도를 또 옮기면 결국 원래의 0/90/180/270도를 그대로 다시 보는 것과 같아서 실질적으로 새로운 영역을 전혀 못 봤습니다(로그에서 재시도 3번 다 원래와 똑같이 전부 "NO"만 나온 이유). **수정**: 재시도 시 반 스텝(45도)만 옮기도록 바꿔서, 원래 스윕이 건너뛴 45/135/225/315도 방향을 실제로 확인하도록 했습니다.

### 출입구 우선 탐색 + 절대 자동 중단 안 함 + 로봇 실제 크기 반영 (2026-07-27, 5차)

4차 수정 이후에도 실기 로그를 보면, VLM이 문/복도를 잘 찾아내는데(`GO:YES`) 실제로 그 방향에 전진하면 매번 depth 센서 임계값(0.6m)에 걸려 좌절되고, 결국 두 후보 다 소진되면서 "사무실 중앙" 반경 1m 안에서만 맴돌고 있었습니다. 근본 원인은 **로봇 실제 크기(가로세로 18cm, 높이 25cm)에 비해 0.6m 정지거리가 지나치게 보수적**이었던 것 - 가구가 촘촘한 사무실에서는 이 임계값 때문에 실제로 지나갈 수 있는 대부분의 틈이 "막힘"으로 잡혔습니다.

**수정**:
- `depth_nav_node.obstacle_stop_distance_m`을 0.6m → 0.3m로 낮췄습니다(로봇 몸체 크기만큼의 여유, 기존의 3배가 아니라).
- 로봇 실제 크기(`robot_width_m`/`robot_length_m`/`robot_height_m`, 18/18/25cm)를 새 파라미터로 추가해서 VLM에게 보내는 모든 판단 프롬프트(방향별 스캔, 장애물 재확인)에 실제 치수를 명시했습니다 - 이전엔 "폭 약 15cm"로 대충 적어뒀던 것도 정확한 값으로 교체.
- **출입구를 최우선 목표로 탐색**: 방향별 질문을 "이동 가능/불가"만 묻던 것에서 **`DOOR:YES`(문/다른 방으로 이어지는 출입구) / `FLOOR:YES`(그냥 열린 바닥) / `NO`(막힘)**로 세분화했습니다. 이동 후보를 고를 때(`room_scan_pick_doorway`) 출입구 후보가 하나라도 있으면 무조건 그것부터 시도하고, 출입구가 하나도 없을 때만 열린 바닥으로 대체합니다. CSI 천장 질문에도 "조명/재질이 바뀌는 경계(=문일 가능성)"를 같이 물어보도록 보강했습니다.
- **탐색은 통로가 막혀서 스스로 멈추지 않습니다**: 루트 지점에서 갈 곳을 다 못 찾으면 이전엔 `explore_room_scan_max_root_retries`(3회) 후 "탐색 완료"로 STOPPED 처리했는데, 이제 그 상한을 없애고 **0.5/0.25/0.75 스텝(45/22.5/67.5도)을 순환하며 무한히 재탐색**합니다. 관리자가 명시적으로 "정지"를 보내기 전까지는 절대 스스로 멈추지 않습니다.

### 출입구를 찾고도 완전히 통과하기 전에 포기하던 문제 + 명령 오인식 (2026-07-27, 6차)

5차 수정(0.3m 정지거리) 이후 실기 로그를 보니 **장애물 임계값 때문에 멈추는 문제는 사라졌지만**(이번 로그엔 "장애물 재확인" 자체가 한 번도 안 나옴 - depth 임계값 완화가 효과 있었음), 여전히 "사무실 중앙"/"사무실 조금안쪽" 두 라벨 사이만 계속 맴돌았습니다. 정확한 원인:

- 매번 첫 스윕에서 `출입구: YES`(문과 복도 연결됨)를 정확히 찾아내고 그 방향으로 이동을 시작하는데, **`explore_room_scan_advance_seconds`(4초, 느린 속도) 한 번의 전진으로는 실제 문까지 도달하지 못한 채 방 한중간에서 멈췄습니다.** 그 자리에서 "같은 공간인지" 재확인하면 당연히 `NEWROOM:NO`(아직 같은 방)가 나오는데, 기존 코드는 이걸 "이 방향은 틀렸다"고 오해하고 **완전히 다른 방향으로 갈아탔습니다** - 정확히 찾아낸 출입구를 끝까지 밀어붙이지 않고 매번 포기한 것이 진짜 원인이었습니다.
- 관리자가 "왜 멈춰? 계속 탐색해"라고 보냈는데 `mission.py`의 직접 명령 매처가 "탐색"+"멈춰"가 같이 있다는 이유만으로 **정반대로 `explore_stop`(탐색 중지)로 해석**해버렸습니다(실기 로그로 확인됨).

**수정**:
- `room_scan_same_room_continue()`: 방금 이동한 방향이 `DOOR`(출입구)로 분류된 곳이었다면, "아직 같은 방"이라는 판정이 나와도 다른 방향으로 갈아타지 않고 **같은 방향으로 계속 전진**합니다(`explore_room_scan_max_door_chase`, 기본 4회까지). `FLOOR`(그냥 열린 바닥)였을 때만 기존처럼 다른 방향을 찾습니다 - 애초에 "어딘가로 이어진다"고 주장한 적이 없으니까요.
- `mission.py`: "계속"이 포함된 문장은 "정지"/"멈춤" 단어가 같이 있어도 우선적으로 탐색을 **계속**하는 것으로 해석하도록 순찰/탐색 두 명령 모두 고쳤습니다.

### 위치/지도 삭제 기능 추가 (2026-07-27, 7차)

반복된 버그로 쌓인 중복 라벨("사무실 중앙"이 여러 번 저장됨)을 정리할 방법이 없었습니다. 관리자 채팅으로 아래 명령을 새로 지원합니다.

세 명령 모두 `mission.py`의 직접 매칭 + `llm_control_node`의 LLM 해석 양쪽에 다 추가했습니다.

### 회전각 재보정 #3 + 장애물 회피-탈출 스캔 추가 (2026-07-27, 8차)

사용자가 "1회 회전시 120도 가까이 하고 있어. 90도 회전하도록 모터 회전을 줄여"라고 실측 결과를 보고했습니다. 7차까지는 `explore_room_scan_angular_speed=0.09` + `explore_room_scan_turn_seconds=1.0`이 실제로 90도라고 가정하고 `explore_room_scan_headings`를 4로 맞췄는데, 실측하니 그 조합이 실제로는 ~120도였습니다. 회전속도는 그대로 두고(사용자 지시대로 "모터 회전을 줄여" = 회전 시간을 줄이라는 뜻으로 해석) `explore_room_scan_turn_seconds`를 1.0 → 0.75(= 90/120 × 1.0)로 조정했습니다. 인코더가 없어 매번 실측-보정이 필요한 값이라, 이후에도 실측 결과가 어긋나면 같은 비율 계산으로 재조정하면 됩니다.

또한 "막혔다고 판단될때 천천히 회전하며 영상분석을 통해 빠져나올수 있도록 해. 뒤에 길이 있는데 그냥 멈추고 있어"라는 문제도 보고됐습니다. 원인: 전진 중 장애물에 막혀 `room_scan_abort_advance()`가 호출되면, 기존에는 그 방(room)의 최초 4방향 스윕에서 이미 기록해둔 "미시도" 후보 목록(`untried_movable`)에서만 다음 방향을 골랐습니다 - 그 스윕이 애초에 샘플링하지 않은 방향(예: 정확히 로봇 뒤쪽)에 실제로 길이 있어도 절대 고려되지 않았고, 남은 후보가 없으면 그냥 멈춰있는 것처럼 보였습니다. `room_scan_abort_advance()`가 바로 다음 후보로 넘어가는 대신 새로운 "탈출 스캔" 단계(`room_scan_begin_escape_step`)를 먼저 실행하도록 고쳤습니다: 제자리에서 0.25스텝(~22.5도)씩 천천히 회전하며 매 정지 지점마다 VLM에 새로 물어보고(`DOOR:YES`/`FLOOR:YES`/`NO`), 지나갈 수 있는 방향을 찾으면 바로 그쪽으로 전진, 한 바퀴(4스텝×4=16회) 다 돌아도 못 찾으면 기존의 스테일(stale) 후보 목록으로 최종 폴백합니다. `room_scan_process_vlm_step_result()`에 `room_scan_escape_active` 분기를 추가해 이 탈출-스캔 중의 관측은 영구 관측 목록에 기록하지 않도록(재사용 목적이 아니므로) 분리했습니다.

### "라벨 저장 직후 멈춤"의 진짜 원인 발견 및 수정 (2026-07-27, 9차)

실기 로그로 마침내 재현 가능한 원인을 찾았습니다. 방 라벨을 저장한 직후("방 라벨 저장: 작은방"), 로그에 이런 순서가 찍혔습니다:

```
robot'YES, 바닥 열린 공간' 방향(천장 힌트: 우)으로 이동합니다   <- 정상, 이동 재개
robotvisual features captured for 작은방 (211 keypoints)          <- 정상, 라벨=위치로도 등록
llm{"source": "llm", "prompt": "작은방", "command": {"type": "inspect", ...}}  <- 문제!
robotcommand routed by llm: {"type": "inspect", "target": "작은방", ...}
robot'작은방' 좌표로 이동 시작 ...                                <- EXPLORING에서 강제로 빠져나감
```

**원인**: `patrol_node`와 `llm_control_node`는 서로 다른 프로세스로, 둘 다 같은 `/ccai/admin_text` 토픽을 독립적으로 구독합니다. 관리자가 라벨("작은방")을 답장하면 `patrol_node`는 `room_scan_awaiting_label` 상태로 이걸 정상적으로 라벨 답변으로 소비하지만, `llm_control_node`는 그 상태를 전혀 모르는 채로 똑같은 텍스트를 "일반 명령"으로 간주해 LLM에 보냈고, LLM은 (문맥 없이) 이를 "작은방을 점검하러 가라"는 `inspect` 명령으로 해석했습니다. 그 결과 로봇이 `EXPLORING` 상태에서 강제로 `INSPECTING`으로 전환되어 탐색 틱(`tick_room_scan`)이 멈췄고, "라벨링 한 번 하고 멈춤"으로 보였던 것입니다. 이전 회차들에서 반복 보고된 "또 멈춤" 현상들도 대부분 이 버그가 원인이었을 가능성이 높습니다 (라벨을 물어보고 답을 받는 매 사이클마다 발생하는 구조적 문제라서).

**수정**: `patrol_node`가 라벨 답변을 기다리는 동안(`awaiting_label` 또는 `room_scan_awaiting_label`) `/ccai/awaiting_label`(Bool) 토픽으로 그 상태를 방송하도록 추가(`publish_awaiting_label_state()`, 상태 변경되는 모든 지점에서 호출). `llm_control_node`는 이 토픽을 구독해 `robot_awaiting_label`이 True인 동안 들어오는 admin_text는 아예 LLM/명령 해석 파이프라인에 넘기지 않고 무시하도록(`on_admin_text` 최상단에서 조기 반환) 수정했습니다 - 그 텍스트는 `patrol_node` 쪽에서 이미 라벨로 처리되므로 이중 처리를 막는 것이 목적입니다.

이동제어의 영상분석 기반 LLM 개입은 이미 여러 지점에 구현되어 있습니다: 매 헤딩의 DOOR/FLOOR/NO 판단, 장애물 재확인(PASS:YES/NO), 같은-방 여부 판정(NEWROOM:YES/NO), 8차에서 추가한 장애물 탈출 스캔(막히면 미세 회전하며 매번 새로 영상분석). 이번 근본 원인(라벨 응답 이중 처리)이 해소되면 이 파이프라인이 온전히 끝까지 실행될 것으로 예상합니다.

### 장애물 후진-회전 탈출 + D435i 오버레이 원근 보정 (2026-07-27, 10차)

"장애물에 부딪치고 있어"라는 재보고에 대해: 8차에서 추가한 탈출 스캔은 장애물을 만난 바로 그 자리에서 곧바로 제자리 회전을 시작했는데, 이 로봇 섀시가 완벽한 점-피벗이 아니라서 이미 물체에 바짝 붙은 상태에서 회전하면 스치거나 부딪힐 수 있습니다. `room_scan_abort_advance()`가 탈출 회전 스캔(`room_scan_begin_escape_step`) 전에 `room_scan_begin_escape_backup()`(새 `escape_backup` 단계, `explore_room_scan_escape_backup_seconds`=1.5초 후진)을 먼저 거치도록 수정했습니다 - "회전, 후진후 회전등 로봇 크기를 고려" 요청 반영. 후진 방향은 깊이 센서가 보지 않는 쪽이라 별도 장애물 체크 없이 안전하다고 가정합니다(후방 센서 없음, 기존 한계 그대로).

"D435i 주행뷰에서 영상 하단이 왜 빨강색으로 나와?"에 대해: 6차에서 오버레이 ROI를 실제 주행 판단(`analyze_depth`)과 같은 0.35~0.75 밴드로 맞췄지만, 그 밴드 "안에서도" 아래쪽(0.75에 가까운 행)은 카메라가 더 가파른 각도로 바닥을 내려다보기 때문에 실제 장애물이 없어도 원근 때문에 더 가깝게 측정됩니다. 단일 `obstacle_stop_distance_m` 임계값으로는 이걸 실제 장애물과 구분할 수 없었습니다. `build_drivable_overlay()`에서 밴드 위쪽은 `obstacle_stop_distance_m` 그대로, 아래쪽으로 갈수록 `overlay_near_stop_factor`(기본 0.5) 비율까지 선형으로 낮아지는 임계값을 행별로 적용하도록 수정 - 화면 표시 전용 보정이며 `analyze_depth`의 실제 주행 판단(`obstacle_now`)에는 영향을 주지 않습니다.

### 후진 시간 단축, 장애물 회피 반복(스러싱) 보강, TensorRT 원인 조사 (2026-07-27, 11차)

10차 실기 로그 분석 결과 세 가지 문제가 드러났습니다.

1. **"뒤에는 센서가 없어. 후진은 조금만"**: `explore_room_scan_escape_backup_seconds`를 1.5초 → 0.4초로 단축. 후방 센서가 없는 채로 길게 후진하는 것 자체가 위험이라는 지적을 반영했습니다.

2. **"장애물을 전보다 잘 못 피해"**: 로그를 보면 책장/가방이 어질러진 좁은 구역 하나에서 "빠져나갈 길을 찾음(YES)" → 바로 다음 틱에 "PASS:NO"로 거부 → 후진+재회전 이 패턴이 20회 가까이 반복됐습니다. 원인은 탈출 스캔의 헤딩 판단(넓은 시야에서의 DOOR/FLOOR/NO 판단)이 "책장 아래로 바닥이 보인다"와 "실제로 로봇이 통과할 틈이 있다"를 제대로 구분 못 해, 같은 좁은 구역 안에서 매번 그럴듯해 보이는 새 방향을 찾아내지만 실제로는 다 막혀 있는 상황이 반복된 것입니다. `explore_room_scan_max_escape_rounds`(기본 3)를 넘겨 연속으로 실패하면, 같은 자리에서 미세 회전을 반복하는 대신 `explore_room_scan_deep_backup_seconds`(기본 2.0초)만큼 더 크게 후진해 그 어질러진 구역 전체에서 벗어난 뒤, 이미 알고 있던 다른 방향(또는 room-레벨 재탐색 스윕)으로 넘어가도록 수정했습니다 (`room_scan_abort_advance`의 라운드 카운터 + `room_scan_begin_escape_backup(deep=True)`).

3. **"TensorRT 엔진이 실패하는 원인"**: `scripts/container_build.sh`의 pycuda 설치 로직을 살펴본 결과, 실패를 기억해두는 마커 파일(`pycuda_build_failed`)이 이전(예: xlocale.h 수정 이전) 실패 시점부터 그대로 남아있으면, 그 원인이 이미 고쳐졌어도 매번 재시도 없이 계속 건너뛰기만 하는 구조적 문제를 발견했습니다 - 로그의 "No module named 'pycuda'"가 매번 반복 보고된 것과 정확히 일치하는 패턴입니다. 수정: (a) 마커 파일명을 `_v2`로 올려서 이번 수정이 최소 한 번은 다시 시도되도록 하고, (b) pip 소스 빌드 이전에 플랫폼 apt 패키지(`python3-pycuda`, 사전 빌드된 바이너리라 이 클래스의 빌드 실패 자체를 우회)를 먼저 시도하도록 하고, (c) 빌드가 실패하면 그 이유(pip 에러 로그 마지막 40줄)를 마커 파일 안에 남겨서 다음에 실패 원인을 바로 확인할 수 있게 했습니다. (참고: YOLO ONNX CPU/CUDA 양쪽 다 실패하는 별도 문제 - "scale_shift"/"shape_utils total" 어서션 - 는 OpenCV 4.5.0의 DNN 임포터가 YOLOv8 export의 DFL 헤드 연산(Split/Slice/Reshape 조합)을 온전히 지원하지 못해서 생기는, TensorRT와는 별개의 더 근본적인 모델 포맷 호환성 문제로 보입니다 - 이번엔 손대지 않았습니다.)

### 탈출 로직 재설계, 안전마진/바닥장애물 인식 강화, 천장 엣지 오버레이, 탐색/순찰 정지 혼동 수정 (2026-07-27, 12차)

11차의 "라운드 캡 + 더 깊은 후진" 방식은 실기에서 바로 다음 문제를 일으켰습니다: "후진후 앞에 공간이 생기니, 다시 앞으로가며 반복하고 있어서 빠져나오지 못해. 앞이 막혀서 후진했으면 앞은 이미 막힌 곳이야." 원인은 미세 회전(0.25스텝) 탈출 스캔이 최대 시도 횟수(16회 = 정확히 한 바퀴)를 다 채우면 헤딩이 원래 막혔던 방향으로 그대로 돌아오는데, 마침 후진한 직후라 그 방향이 일시적으로 "열림"으로 다시 읽혀 똑같은 장애물로 재돌진하는 것이었습니다. **탈출 스캔(미세 회전 재탐색) 메커니즘 전체를 제거**하고 훨씬 단순하고 견고한 방식으로 교체했습니다: 막히면 짧게 후진(`explore_room_scan_escape_backup_seconds`=0.4초) → 180도(스윕의 절반) 회전해서 온 길 방향으로 돌아섬 → 이미 알고 있던 다른 방향으로 이동(`room_scan_advance_after_label`, 방금 막힌 방향은 이미 "시도됨"으로 표시되어 있어 재선택되지 않음). `explore_room_scan_max_escape_rounds`/`explore_room_scan_deep_backup_seconds`와 관련 상태(`room_scan_escape_active` 등)는 모두 삭제.

추가로 이번 라운드에 반영한 것들:

- **"장애물을 여전히 부딪혀... 순찰 로봇이라 벽에 가까이 가지 않아도 돼. 상태만 확인하면 돼"**: `obstacle_stop_distance_m`을 0.3m → 0.45m(코드 기본값)로 되돌림 - 이 로봇은 순찰이 임무지 좁은 틈을 억지로 통과할 필요가 없다는 지적을 반영, 안전마진을 우선.
- **"바닥 장애물 인식을 너무 못해. 인식률을 올려"**: `depth_nav_node.py`의 `analyze_depth`에서 (a) 분석 밴드를 0.35~0.75 → 0.35~0.85로 넓혀 로봇 바로 앞 낮은 장애물도 잡히게 하고, (b) 장애물 판정을 센터 열만 보던 것에서 좌/중/우 중 하나라도 임계값 아래면 정지하도록 바꾸고, (c) "너무 가까워 값이 안 잡히는" 클러스터 판정 기준을 10%→4%로 낮춰 얇은 물체(케이블, 책 등)도 더 잘 잡히게 함. `build_drivable_overlay`의 ROI도 같은 0.85로 맞춤(원근 보정 taper는 유지되어 맑은 바닥은 여전히 초록으로 표시).
- **"천장 CSI카메라에... 엣지를 통해 천장 모양을... LLM에 보내서 분석"**: `vlm_client_node.py`에 `image_overlay` 파라미터(기본 "none") 추가 - "edges"로 설정하면 전송 전 Canny 엣지 검출을 프레임에 오버레이(하이라이트)해서 보냄. CSI 인스턴스(`vlm_client_node`)에만 `image_overlay: "edges"`로 켰습니다. YOLO는 COCO 객체 클래스(사람/의자 등)라 "천장 구조" 자체를 검출할 개념이 없고 현재 ONNX 문제로 고장난 상태이기도 해서, 이번엔 엣지 검출만 구현했습니다 - YOLO 활용은 별도로 TensorRT/ONNX 문제가 먼저 해결돼야 의미가 있습니다.
- **"탐색과 순찰을 혼동하고 있어... '중지' 명령을 내리면 patrol_stop을 하고 있어"**: `mission.py`에서 무조건 `patrol_stop`으로 매핑되던 맨 "정지"/"멈춰"(순찰/탐색 명시 없음)를 새 `stop` 타입으로 분리하고, `patrol_node.py`가 현재 상태(`EXPLORING`이면 탐색 중지, 아니면 순찰 중지)에 따라 실제로 실행할 동작을 결정하도록 수정(`stop_patrolling()`/`stop_exploring()` 헬퍼로 분리). "순찰 중지"/"탐색 중지"처럼 명시적인 표현은 그대로 각각의 타입으로 고정.

### 아직 검증 안 된 것 (정직하게, 실기 테스트 전)

- **12차 수정(탈출 로직 재설계, 안전마진 0.45m, 바닥장애물 인식 강화, 천장 엣지 오버레이, stop 컨텍스트 인식) 실기 미검증**: 이 절 작성 시점에 아직 로봇에서 돌려보지 못했습니다. 특히 후진(0.4초)+180도 회전이 실제로 "온 길로 돌아가는" 것처럼 보이는지, 밴드 확장(0.85)이 오탐(맑은 바닥을 막힘으로 오판)을 너무 늘리지는 않는지, 엣지 오버레이가 LLM의 천장 판단에 실제로 도움이 되는지 확인 필요.
- **11차 수정(후진 0.4초, TensorRT 마커/apt 우선 시도) 실기 미검증**: apt로 `python3-pycuda`가 이 플랫폼 저장소에 실제로 존재하는지조차 확인 못 했습니다 - 없으면 기존 pip 빌드 경로로 자동 진행되지만, 로봇에서 직접 컨테이너를 재시작해 로그를 봐야 실제 동작을 알 수 있습니다. (라운드 캡/깊은 후진 부분은 12차에서 재설계로 대체됨.)
- **10차 수정(후진-회전 탈출, 오버레이 원근 보정) 실기 미검증**: 이 절 작성 시점에 아직 로봇에서 돌려보지 못했습니다 - 1.5초 후진이 실제로 물체와 충분한 거리를 만드는지, 오버레이가 실제로 바닥을 녹색으로 정확히 표시하는지 확인 필요.
- **9차 수정(라벨 응답 이중 처리 버그) 실기 미검증**: 근본 원인을 코드/로그로 명확히 특정했지만, 수정 후 실기에서 라벨 저장 이후 탐색이 실제로 끊기지 않고 계속되는지 확인 필요.
- **8차 수정(회전각 0.75초 재보정, 장애물 탈출 스캔) 실기 미검증**: 이 절 작성 시점에 아직 로봇에서 돌려보지 못했습니다 - 0.75초가 실제로 90도에 가까운지, 탈출 스캔이 실제로 막힌 상황에서 빠져나오는지 확인 필요.
- **위치/지도 삭제 기능 실기 미검증**: 명령 파싱 패턴과 실제 삭제 동작 모두 이 절 작성 시점에 아직 로봇에서 돌려보지 못했습니다.
- **6차 수정 실기 미검증**: 출입구 추적(door chase) 로직과 "계속" 명령 파싱 수정 모두 이 절 작성 시점에 아직 로봇에서 돌려보지 못했습니다. 사용자가 6차 수정 이후에도 "또 멈춰서 탐색을 안 함"을 보고했는데, 코드 재검토로는 상태기계에 뚜렷한 새 결함을 못 찾았습니다 - 최신 코드가 실제로 배포됐는지(빌드 캐시 문제 재발 가능성 - 이번 세션에 여러 번 있었음) 확인이 우선이고, 그래도 재현되면 로그가 필요합니다.
- **5차 수정(0.3m 정지거리, DOOR/FLOOR 구분, 무한 재탐색) 검증 진행 중**: 이번 로그로 장애물 관련 멈춤은 재현 안 됐지만(개선 신호), 0.3m가 여러 환경에서 계속 안전한지는 계속 지켜봐야 합니다.
- **4차 수정(같은 방 재확인, 45도 재시도) 실기 미검증**: 이 절 작성 시점에 아직 로봇에서 돌려보지 못했습니다 - `NEWROOM:YES`/`NEWROOM:NO` 판단 정확도, 반 스텝 회전이 실제로 45도에 가까운지 확인이 필요합니다.
- **LLM 장애물 재확인 로직 실기 미검증**: 3차 수정도 아직 로봇에서 돌려보지 못했습니다 - `PASS:YES`/`PASS:NO` 파싱, 재개 후 실제로 무사히 통과하는지 확인이 필요합니다.
- **v3 전체 파이프라인 실기 미검증**: 천장 힌트 기반 방향 선택과 "모든 방향 특징 기억"은 이 절 작성 시점에 아직 로봇에서 돌려보지 못했습니다.
- **"이동 중 새로운 것 발견 시 즉시 정지" 미구현**: 위 파이프라인 설명대로, 실시간 감지가 아니라 "매 지점 도착 시 재스윕"으로 단순화했습니다 - 이동 경로 중간에 있는 것은 도착 스윕에서야 인식됩니다.
- **천장 방향 힌트 파싱 신뢰도**: "방향:왼쪽" 같은 형식으로 답해달라고 요청했지만 LLM이 항상 그 형식을 지킬 보장은 없고, 못 찾으면 그냥 스윕 순서상 첫 번째 이동가능 방향으로 폴백합니다 - 힌트가 실제로 얼마나 자주 유용하게 파싱되는지 실측 필요.
- **회전/이동 시간 캘리브레이션 미완료**: `explore_room_scan_turn_seconds`(1.0초)/`explore_room_scan_angular_speed`(0.09)/`explore_room_scan_advance_seconds`(4.0초)/`explore_room_scan_linear_speed`(0.03) 전부 첫 추정치이고 실기로 맞춰야 합니다.
- **VLM 응답 지연이 탐색 속도를 좌우**: 이전 세션에서 VLM 백엔드(H200 프록시) 연결이 간헐적으로 느리거나 끊긴 전례가 있습니다(`docs/vision_and_alerts.md` 참고). `explore_room_scan_vlm_timeout_seconds`(15초)는 로컬에서 포기하는 시점일 뿐이고, `vlm_client_node`의 실제 HTTP 타임아웃(35초)이 더 길어서 응답이 오래 걸리면 다음 스텝 트리거가 그 사이 큐잉되어 밀릴 수 있습니다 - 탐색이 유독 오래 걸리거나 멈춘 것처럼 보이면 VLM 백엔드 연결 상태부터 확인하세요.
- **다중 이동가능 방향/복잡한 위상 구조**: 그래프에 순환(같은 지점으로 두 경로가 이어지는 경우)이 있으면 지금 구현은 그걸 감지하지 못하고 같은 곳을 새 지점으로 중복 등록할 수 있습니다 - 위치 재인식(기존 ORB 시각 특징 매칭)과의 연동은 아직 없습니다.
